## Why we're restarting

- nosh began as a beginner project to learn React, Node.js and AI-assisted
  development. The owner has since grown as an AI developer, and the models have improved.
- Goal, in the owner's words: **"a better app that is easier to work on and uses
  the latest flows I've learnt."**
  - *Better app*: chiefly the UI/UX. The current one "feels clunky and
    unprofessional".
  - *Easier to work on*: easier for the owner plus AI agents, meaning a smaller,
    conventional codebase, tests as the spec, and lean docs.
  - *Latest flows*: superpowers end to end (brainstorm → spec → plan →
    red-green TDD → review), one feature group at a time.
- **Learning React/Node is no longer a goal.** The original stack was picked for
  the job market. Tech is now chosen on merit for the app and for agent-friendliness.

### Stack shape 1 (as proposed and accepted)

- Frontend: React + TypeScript SPA, Vite, TanStack Router + TanStack Query,
  Tailwind, shadcn/ui (Base UI), Motion. PWA (installable on iPhone).
- Backend: Hono (serves the API *and* the built SPA, so one deployable).
  Shared zod schemas plus Hono's typed RPC client for end-to-end types.
- Data: PostgreSQL (kept), Drizzle ORM + migrations.
- Jobs: Postgres-backed queue (pg-boss) for imports.
- Tests: Vitest (unit/integration) + Playwright (`@playwright/test`, e2e).
- Rejected: React Router v7 framework mode (SSR not needed for a private
  single-user app, and it couples routing/data/service worker); Next.js
  (Vercel/RSC complexity for no gain); a non-TS backend (Go/Python) because two
  languages would lose shared types. Go is the credible alternative if the
  backend ever separates.
- Why React/TS: AI models are measurably more reliable on popular stacks
  ("Matthew effect", ICLR 2026, arXiv 2509.23261). TypeScript is #1 on GitHub
  (Octoverse 2025). The AI app builders (Lovable, v0, Bolt) standardised on
  React + TS + Tailwind + shadcn. Principle carried forward: **prefer boring,
  popular libraries over the newest ones.**

### My proposals: put to the owner, not yet explicitly confirmed

The owner asked for this handover right after these were proposed. Treat them
as the default and list them in the design doc for confirmation:

1. **Project order:** (1) restart design doc → (2) spec extraction → (3) archive
   and wipe → (4) build, one superpowers cycle per feature group → (5) data
   migration and cutover.
2. **Spec extraction:** parallel agents per area (auth, recipes, collections,
   search, import, units/scaling/translation, settings, PWA/push, security
   hardening). They read the current code, tests and `docs/decisions.md` (54
   ADRs) and produce testable acceptance criteria (the *what*), the rationale
   (the *why*) and a keep/drop line per feature. Capture what nosh does, not
   how it's built. **Gate: nothing is wiped until the owner approves the spec.**
3. **Build order:** skeleton + auth → recipes → collections → search → units
   and scaling → import jobs → PWA and push → settings.
4. **Migration and cutover:** a one-time importer (old schema → new), built
   test-first against a sanitised dump of the real DB. The new container runs
   alongside the old one on its own DB; import, verify, switch Caddy; rollback
   means pointing Caddy back. A few minutes of downtime is acceptable (single user).
5. **Security hardening carries over as explicit requirements**: SSRF guard
   (URL import, yt-dlp, Web Push), `__Host-` session cookie, origin checks,
   rate limits.
6. **Accounts stay** (parity), single-user in practice, using **Better Auth**
   (with its Drizzle adapter) instead of hand-rolled sessions.
7. **Leaner docs:** new repo starts with a short `CLAUDE.md`, the design doc and
   the specs. The old docs live on in the `legacy` branch.
8. **Navigation** (planner dropped): library-only app, floating bottom bar
   reduced to Library + mustard "+" (new recipe / import), settings icon
   top-right. Final shape to settle in the design doc.

## Current app: facts relevant to the rewrite

- Monorepo (pnpm): `frontend/` (React 19 + Vite + Tailwind 4, PWA),
  `backend/` (Express 4, pg, node-pg-migrate, express-session +
  connect-pg-simple, argon2, multer, cheerio, web-push, zod),
  `packages/units` (`@nosh/units`).
- Features today: accounts (username/password); recipes with photos,
  tags, servings, times, scaling and unit conversion; nested mandatory
  collections as the home page (recipes may live at Home); Postgres full-text
  search (`english` config, which is poor for Dutch); weekly meal planner
  (**dropped**); Gemini import from URLs (JSON-LD fast path), Instagram Reels
  and TikTok (yt-dlp), run as server-side jobs with NDJSON progress and a Web
  Push "done" notification; auto-translation and unit conversion of imports;
  per-user recipe language/unit preferences; per-user Gemini model choice
  and a self-counted usage estimate.
- Deployed on the owner's homelab (Docker via Dockge, behind Caddy) at
  `https://nosh.itsthomassito.com`; the image is pulled by Watchtower.
- Docs: `docs/index.md` (overview), `docs/decisions.md` (54 dated ADRs: the
  main source of the *why*), `docs/backlog.md`, `docs/architecture.md`,
  `docs/deployment.md`, `docs/handover/` (release runbooks).
- Open backlog items that may matter later (not in the first release): notes
  and ratings, cook mode, grocery lists, nutrition, Belgian supermarket
  integration, Dutch-aware search, volume↔weight conversion, locale decimals,
  CSP header.
